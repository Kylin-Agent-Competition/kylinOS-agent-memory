**结论**：失败工具调用在真实宿主（5.0.3）中已观测到，失败事件真实存在。

## 四、关键发现（对 Hook / 日志回调设计的提示）

**失败 tool_result 无结构化错误标记**：失败的 `tool_result`（`31567`）与成功的 `tool_result`（`31758`）JSON 结构完全一致，均为 `{id, name, output, type:"tool_result"}`，**没有 `is_error` / `error_code` / `status` 字段**。

- 失败只能通过解析 `output` 文本（本例为「权限不够」）推断，无法结构化区分成败。
- 这意味着「失败不沉淀知识」的判定在 Hook 层**不能依赖宿主提供的字段**，必须在 `ToolExecutionEvent` 侧补充失败判定逻辑（解析 output 或补充上游字段）。
- 该缺口与此前 `d4_openkylin_remediation/tool_hook_audit.md` 记录的源码缺口（`toolReply` 缺 `arguments`/`tool_call_id`/`cancelled` 等）一致，方向吻合。

## 五、诚实结论与边界

### 已证明（本轮补测新增证据）

1. **失败工具调用在宿主真实发生**（`ls -la /root` → `权限不够`，有完整 tool_call/tool_result 日志）。
2. **宿主日志全文无任何知识沉淀/知识候选记录**（否定性证据，失败后同样无）。

### 未证明 / 不能归因（证据边界）

- 「失败不沉淀」的**端到端逻辑**仍无法验证：本项目 **Hook 与 Memory Service 尚未集成到宿主**（`evidence/index.yaml` AGT-004-5.0.3-001 已注明），宿主本身不产生知识候选。因此日志中「无沉淀」**无法区分**是「失败被正确拦截」还是「沉淀机制本身未接入」。
- V5-3 因此**不能**标记为「✅ 已验证」，只能标记为「⚠️ 部分证据：失败场景已真实观测 + 宿主日志无沉淀」。

### 解除完整验证的前置条件

1. 本项目 Tool Hook 集成到宿主（捕获 `ToolExecutionEvent`，且需补齐失败判定/`is_error` 字段）。
2. Memory Service 落库打通（知识候选列表可查询）。
3. 在上述链路就绪后重跑 V5-3：失败工具 → 查询知识候选列表 → 断言「不含成功记忆，仅 FailureMemory」。
